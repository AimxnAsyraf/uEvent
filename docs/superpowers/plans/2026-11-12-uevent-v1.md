# uEvent v1 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the first version of uEvent: clubs submit event proposals, the SRC reviews them, approved events are published, and clubs file post-event reports.

**Architecture:** A single Next.js App Router application. Business rules live as pure TypeScript functions in `src/domain/` and are unit-tested. Every write goes through a server action in `src/features/<area>/actions.ts`, which authorises the caller with the domain functions and then writes with the Supabase service-role client. Row Level Security allows reads only, as a second line of defence; anonymous visitors can read only the `public_events` view.

**Tech Stack:** Next.js 16, React 19, TypeScript, Tailwind CSS 4, Supabase (Postgres, Auth, Storage) with `@supabase/supabase-js` 2 and `@supabase/ssr`, Zod 4, Resend for email, Vitest 5, Playwright. Hosting: Vercel and a Supabase cloud project.

**Spec:** `docs/superpowers/specs/2026-11-12-uevent-design.md`

## Milestones

| Milestone | Tasks | Outcome |
|---|---|---|
| M1: SRC demo | 1 to 9 | A club drafts and submits a proposal; the SRC approves, returns or rejects it. |
| M2: Complete v1 | 10 to 14 | Letter verification, public page, change requests, reports, SRC overview. |
| M3: Pilot ready | 15 | Deployed, with real sign-in, ready for 3 to 5 pilot clubs. |

With 3 to 4 developers: Tasks 1 and 2 are done first by the whole team. After that, Tasks 3 and 4 (domain), 5 and 6 (accounts) and 8 (notifications) can run in parallel. Tasks 10 to 14 can run in parallel once Task 9 is merged.

## Global Constraints

- Node.js 22. Use the latest stable release of each package in the tech stack at scaffold time and commit the lockfile.
- Only email addresses ending in `@utp.edu.my` may have accounts. Compare case-insensitively.
- All server actions return `ActionResult<T>` (Task 1) and never throw for expected failures.
- No client code writes to the database or to storage directly, except uploading to a signed upload URL issued by a server action.
- The service-role key is used only in `src/lib/supabase/admin.ts`, which starts with `import 'server-only'`.
- Store timestamps as `timestamptz` in UTC. Display them in `Asia/Kuala_Lumpur` using `formatDateTime` (Task 1).
- Money is in RM, stored as `numeric(12,2)`.
- English only. Status labels shown to users come from `STATUS_LABELS` (Task 3).
- Uploads: at most 10 MB each. Documents: PDF, DOCX, JPG, PNG. Posters: JPG, PNG.
- Defaults: notice period 3 days, report due 14 days after the event ends. Both are read from the `settings` table.
- Commit after every task with a Conventional Commits message.

## Review Focus

1. **Two SRC admins decide the same proposal at the same moment.** The second must get an "already decided" error; there must be one history row and one set of notifications. Test in Task 9.
2. **Uploads that are too large, of the wrong type, or aimed at another club's event.** Each must be refused before a signed URL is issued, and an attachment must not be recorded for a file that was never uploaded. Test in Task 7.
3. **Email case and non-university addresses.** `Ali_12345@UTP.EDU.MY` must match an invitation sent to `ali_12345@utp.edu.my`; `x@utp.edu.my.evil.com` and `x@gmail.com` must be refused. Tests in Tasks 2 and 5.
4. **A hostile sign-up link.** `javascript:alert(1)` or an `http:` link must be refused; only `https:` links are stored and rendered. Tests in Tasks 7 and 11.
5. **Leaving a club without a president.** Removing the president, or the president removing themselves, must be refused; transfer must leave exactly one president. Test in Task 6.
